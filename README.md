# Stock Control для сети шаурмы «Сочный вертел»

Учебный проект: приложение на Python (Streamlit), которое помогает закупщику сети быстрее и точнее заказывать ингредиенты и видеть, где теряются деньги.

> **Важно.** «Сочный вертел» взят как учебный кейс. Реальные данные компании не использовались. Все цифры (цены, нормы, продажи, потери) **синтетические** и нужны только для демонстрации метода. Целевые показатели эффекта в документации являются гипотезами.

## Бизнес-проблема

Заказы поставщикам и контроль расхода ведутся вручную и по опыту. В результате:

- скоропортящиеся продукты (мясо, овощи, соусы) списываются по сроку годности;
- ингредиент заканчивается на точке, и блюдо снимают с продажи;
- расход выше нормы по техкартам (порча, переборы порций), но этого никто не видит, потому что инвентаризацию собирают, но не анализируют.

## Решение

Приложение сопоставляет **теорию** (продажи × техкарты) с **фактом** (остатки и поставки), считает отклонения в единицах и рублях, классифицирует ингредиенты по ABC/XYZ и рассчитывает рекомендуемый заказ с учётом дня недели.

## Функции

| Вкладка | Что делает |
|---|---|
| Данные | Загрузка демо-данных или своих CSV с проверкой, шаблоны файлов |
| Техкарты | Состав блюд, себестоимость и food cost по блюдам |
| Расход | Теория / факт / отклонение по ингредиентам и точкам, подсветка выше порога, топ потерь, пометка «проверить пересчёт» |
| ABC/XYZ | Классы ингредиентов, матрица 3×3, диаграмма Парето, рекомендации по классам |
| Заказ | Список «заказать сейчас» по поставщикам с выгрузкой в CSV, риск списания |
| Дашборд | KPI: отклонение расхода, потери в ₽, food cost, нехватки, покрытие запаса |

## Как это считается

**Период** между двумя инвентаризациями (по умолчанию понедельник и четверг, в конце дня): дни после первой даты и день второй.

```
Теория  = Σ (продано блюд × норма ингредиента в техкарте)
Факт    = остаток на начало + поставки - остаток на конец
Отклонение = Факт - Теория        (плюс = потери)
```

**Заказ** (страховой запас фиксирован: расход за 1 день):

```
Цель  = расход_в_день × (срок_поставки + горизонт_заказа + 1 день)
Заказ = max(0, Цель - остаток), округлённый вверх до кратности упаковки
```

Расход прогнозируется как среднее за те же дни недели за последние 6 недель, умноженное на коэффициент потерь (факт / теория за последние 4 недели, от 1,0 до 1,5). **Риск списания:** остаток больше, чем уйдёт за срок годности.

**ABC:** по стоимости расхода (A: до 80% накопленной доли, B: до 95%, C: остальное). **XYZ:** по коэффициенту вариации дневного расхода (X до 10%, Y до 25%, Z остальное). Перед XYZ расход очищается от недельной сезонности, иначе предсказуемая разница «пятница выше вторника» выглядела бы как нестабильность. Границы настраиваются на экране.

## Технологии

Python 3.10+, pandas, numpy, Streamlit, Plotly, pytest. Платные сервисы и API не используются, база данных не нужна (данные в CSV).

## Запуск

```bash
# 1. Создать виртуальное окружение (рекомендуется)
python -m venv .venv
# Windows:  .venv\Scripts\activate
# macOS/Linux:  source .venv/bin/activate

# 2. Установить библиотеки
pip install -r requirements.txt

# 3. Запустить приложение
streamlit run app.py
```

Откройте адрес из консоли (обычно http://localhost:8501) и нажмите **«Загрузить демо-данные»** в боковой панели.

Тесты: `pytest`

Пересоздать демо-CSV: `python -m src.demo_data` (файлы появятся в `data/demo/`).

## Свои данные

Нужны 7 CSV-файлов в кодировке UTF-8 (даты в формате ГГГГ-ММ-ДД). Шаблоны с заголовками можно скачать на вкладке «Данные». Пример заполненных файлов лежит в `data/demo/`.

| Файл | Колонки |
|---|---|
| stores.csv | store_id, name |
| ingredients.csv | ingredient_id, name, unit, price_per_unit, supplier, lead_time_days, shelf_life_days, pack_size |
| dishes.csv | dish_id, name, price |
| recipe_items.csv | dish_id, ingredient_id, qty_per_dish |
| sales.csv | date, store_id, dish_id, qty |
| deliveries.csv | date, store_id, ingredient_id, qty |
| inventory.csv | date, store_id, ingredient_id, qty |

## Структура проекта

```
app.py                  точка входа Streamlit
src/
  validators.py         проверка файлов, понятные ошибки с номерами строк
  data_loader.py        чтение CSV и приведение типов
  demo_data.py          генератор синтетических данных
  consumption.py        теория, факт, отклонения, пометка пересчёта
  abc_xyz.py            классификация ABC/XYZ
  ordering.py           прогноз, точка заказа, риск списания
  kpi.py                food cost, себестоимость, KPI
  ui_pages.py           вкладки интерфейса (только показ)
data/demo/              демо-данные (синтетика)
tests/                  тесты ключевой логики
```

Правило архитектуры: интерфейс вызывает расчёты, расчёты ничего не знают об интерфейсе. Поэтому логику можно проверять тестами без запуска приложения.

## Ограничения MVP

- Данные только через CSV, интеграции с кассой и учётной системой нет.
- Техкарты плоские: блюдо состоит из ингредиентов (полуфабрикатов и соусов как рецептур нет).
- Прогноз простой (среднее по дню недели), без ML, учёта акций и праздников.
- Короткие периоды (3-4 дня) дают шумный факт, одна ошибка пересчёта сильно меняет отклонение; такие периоды помечаются «проверить пересчёт».
- Списания отдельно не ведутся: они входят в факт потерь. Доля списаний и время подготовки заказа в приложении не рассчитываются (время замеряется вручную до и после внедрения).
- Метрика «ингредиент заканчивался» считается по остатку на дату инвентаризации, а не по дням.
